Concurrency Pool : Implémenter un ThreadPool résilient en Python

Conception d'une structure de répartition de charge non-bloquante avec gestion de backpressure, isolation de fautes et ordonnancement déterministe sous saturation.

Compétences ciblées
threading.Thread Lock & Condition Backpressure Queue Graceful Shutdown Memory Leak Prevention

1. Contexte du problème & Architecture cible

RFC-089 // ThreadSafety

En environnement micro-services à haut débit, les requêtes IO et les calculs cryptographiques peuvent rapidement épuiser les descripteurs de threads natifs de l’OS. L’implémentation standard ThreadPoolExecutor masque délibérément la rétention de file et les stratégies de saturation mémoire. Votre mission consiste à concevoir un ordonnanceur de niveau production capable de borner strictement l'allocation mémoire, tout en garantissant l'absence totale de dérive en cas d'effondrement d'un sous-système worker.

2. Spécifications & Contraintes du contrat d'API

Class: ResilientThreadPool
warning

Règle d'or : L'import de concurrent.futures est formellement interdit dans le code de production. Seuls les modules de base threading, queue, time et sys sont autorisés.

01

Initialisation & Dimensionnement strict

La méthode __init__(self, max_workers: int = 4, max_queue_size: int = 100, rejection_policy="caller_runs") doit initialiser les structures de données sans démarrer les threads prématurément si un démarrage différé est requis.

02

Stratégie de rejet (Backpressure handling)

Lorsque la file atteint max_queue_size, submit() ne doit ni bloquer indéfiniment ni lancer une exception silencieuse : la tâche doit être exécutée sur le thread de l'appelant (CallerRunsPolicy) pour ralentir la source de production.

03

Extinction déterministe (Graceful Shutdown)

La méthode shutdown(wait=True, cancel_pending=False) doit diffuser un signal sentinelle (Poison Pill) à chaque thread ouvrier. Aucun thread orphelin ne doit persister après l'extinction.

04

Isolation hermétique des pannes ouvrières

Une exception levée par un callback ou une tâche soumise doit être encapsulée dans l'objet PoolFuture. Le thread worker doit rester sain et prêt pour la tâche suivante sans redémarrage de pile.
